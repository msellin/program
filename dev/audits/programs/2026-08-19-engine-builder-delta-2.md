# Engine Builder — DELTA-2 audit (2026-08-19, post-Batch 5/6)

Follow-up to `2026-08-19-engine-builder-delta.md` after commits `05e101b`
(Batch 5, six user-visible fixes) and `33e2061` (Batch 6, positive-adaptation
signal + sim end-date + capability seeds — but the capability seeds are
skill/mobility only, not engine). Two persona bundles compared:

- `persona-engine` — consistent-average, tier=foundation, 60 days
- `persona-engine-fast` — overperformer, tier=progression, 60 days

Both regenerated by harness5.

## 1. Verdict

Batch 5/6 **delivered five of the six items** the DELTA-1 report queued —
`aggregation: "trend_slope"` now flows through, the Report page defaults to
LAST 12W not 3Y, the retest deltas math is now trend-mean-vs-trend-mean (real
signal not noise), the non-responder cluster chip renders "RESPONDING" on
both personas, and `active_program_started_at` correctly lands 60 days
before capture. **But the headline bug from the reconciled list — Today's
contradictory clocks — is still broken because #1 only gated three of the
four surfaces that fire independently on graduated users**, the fatigue
attribution string is unchanged, adherence math still shows 0/15 despite 22
logged runs, and the positive-adaptation signal is coded but never fires
because the sim's HR drift is too gentle to cross the ≥50%-of-target
threshold. Net: the engine now measures the right things but Today still
tells four different stories at once, and the archetype-differentiation the
overperformer was supposed to expose is silent.

## 4. New bugs from persona-engine-fast overperformer path

**Positive-adaptation signal fires nowhere for either archetype (P1 new).**
Batch 6 #7 was purpose-built to give the overperformer a first-class
"consider a tier-up" surface. The code is correct — reads retest
evaluator, requires ratio ≥ 0.5 in the direction-appropriate way. But
for engine-builder the tier target rows are `foundation: -5 bpm`,
`progression: -8 bpm`, `push: -10 bpm`. The overperformer needs to log
4 bpm of drift for -progression to hit the 50% mark; the sim's hardest
overperformer bumps only manage a 2 bpm-real delta over 60 days (the
window is deloaded early and there's noise). **The lever the signal
promised is invisible in the artifact bundle it was built to demonstrate.**
Either lower the threshold to 0.33 for aerobic programs (fires at −2.7/−8
= 0.34 for the fast archetype, which is a real reading), OR bump the sim's
overperformer HR-drift rate to 0.15 bpm/day so the 60d sim clears 50%.
Currently the code lands but the outcome doesn't.

**Confirm-first mechanic invisible for the overperformer archetype (P1
new — deepens DELTA-1's callout).** Persona-engine-fast has zero APPLY
/ IGNORE buttons anywhere in `text/01-today.txt`. No `day_adjustment`
proposal (life_load: 2, no note fatigue → no elevated branch). No
positive-adaptation surface as above. No `tier_advance` (capability_profile
empty → `tier-promotion.ts` bails). No non-responder proposal (Progress
chip says "RESPONDING" — the confirm-first Accept flow isn't triggered).
Landing at `landing/src/i18n/dictionaries/en.ts:48` promises "You log a
note. Engine proposes. You Accept or Ignore." — the overperformer logs 24
sessions and gets zero proposal cards. The mechanic is functionally
present but this archetype never triggers any of its branches.

**GraduationCard fires at week 8+ but retest window is authored at
`at_week: 8`, which the proposal selector counts as weeks 8-9 open —
guaranteed overlap.** `select.ts:333` opens the window `[atWeek,
atWeek + 1]`, `weekNumberFromProgramStart` returns 9 on day 60 of an
8-week arc (60/7 + 1 = 9). `isPastProgramEnd` returns true because
`today (2026-08-19) > phase[7].ends shifted to 2026-08-14`. So a
persona that starts exactly 60 days before capture — a common demo
configuration — will ALWAYS render both cards. This wasn't audit
noise; it's structural. Either:
1. GraduationCard suppresses retest proposals across ProposalStack, or
2. The retest window closes at `phases[-1].ends` regardless of
   `atWeek + 1`, or
3. Retest is authored at `at_week: 7` for engine-builder so the window
   closes before the phase does.

**`RESPONDING` chip renders for both — but the classifier hasn't received
a mid-block baseline.** `HeritageClusterChip.tsx` synthesizes baselines
from `runs[]` (DELTA-1 §5 fix). Both personas cross the low-bar
"responding" verdict but the classifier's real job is to distinguish
under-dosing vs true non-response — neither can render because both
diagnoses require the mid-block second baseline, which never fires
(§3 above). The chip is visually reassuring; the mechanic underneath is
still shallow.

**"WHERE YOU LANDED · Δ −2 bpm" on both personas' post-graduation card
uses point-sample not trend.** `text/01-today.txt:35-37` on -engine shows
`Submax HR at pace-5 · 140 bpm · -2 bpm`. This same card should read the
same trend the Progress panel reads (Δ −1.9 bpm, close but not identical).
Two paths are computing the delta with different math on Today vs
Progress — the "WHERE YOU LANDED" card renders `-2` (rounded integer,
suggesting point-sample) not `-1.9`. Minor but a visible split. Locate the
completion card rendering and route it through
`evaluateRetestMetrics` + `deltaFromBaseline` like the Progress panel
does.

## 5. Recommended next fixes

1. **Gate `retest_due` proposals in ProposalStack on `isPastProgramEnd`.**
   Either `select.ts:selectRetestDueProposal` returns null when the
   program has graduated, OR `ProposalStack.tsx:31` filters `p.kind !==
   "retest_due"` when `isPastProgramEnd(program, date, profile)`. Prefer
   the first — the proposal itself should know it's out of window.
   Closes the P0 that #1 was supposed to close.

2. **Teach adherence + History day-counter to read `runs[]`.**
   `PerProgramAdherenceCard.tsx:50-55` counts scheduled blocks by state;
   add a "log-linked" done tally: for each block whose actual_date has a
   run in `store.logs`, mark it done regardless of scheduled_blocks state.
   Same idea for History's day-level rows — `Object.keys(exercises).filter(done).length + runs.length`. One line each. Highest-value user-facing polish.

3. **Fix the elevated-branch attribution string.**
   `note-signals.ts:249-251` — split the branch: `if (drift) return "…RPE
   drift…"; if (life >= 4) return "…life load ${life}/10…"; else return
   "…fatigue signals in recent notes…"`. One-file edit.

4. **Lower positive-adaptation threshold OR bump the sim.** Signal
   authoring is defensible (50% of target = real signal); sim gentleness
   is the mismatch. Options: (a) drop ratio ≥ 0.5 to ≥ 0.33 for aerobic
   programs where the target is set optimistically vs realistic 60-day
   trajectory; (b) bump the overperformer's daily HR-drift term in
   `simulator-v2.ts` capability seeds to hit −4 bpm by week 8.

5. **Fix `retest_metrics_mid_block[].source_ref` for engine-builder.**
   Either author `runs[].avg_hr where intensity == 'easy'` with
   `window_days: 14` on the mid-block entry (so it computes a real 2-week
   running mean at week 4), or drop the mid-block metric until it can
   compute a real second baseline. Silent JSON entries that render as
   "not yet wired" are inventory bloat.

6. **Route "WHERE YOU LANDED" completion card through
   `evaluateRetestMetrics` + `deltaFromBaseline`.** Both surfaces should
   compute the same number for the same metric — the −2 vs −1.9 split
   is a hint the completion card has its own path.

7. **Simulator: write `started_at` to `program_states[primary_slug]` at
   sim init, not just to extras.** `simulator-v2.ts:265-277` — add
   `started_at: startedAtISO` to the primary's `program_states` merge
   alongside the tier. Not user-visible today but any code that needs
   per-program start (mid-block windowing, retest baseline scoping in a
   multi-program user) fails silently.

8. **Coach copy — depromote the Norwegian 4×4 reference.** Rephrase to
   "Plain-English questions about your training arc, cited to the papers
   the plan uses" — voice-consistent with landing's "cited before shipped".

9. **Retest metric #1 display: rename to "Submax HR on easy days" OR add
   `pace_500m` field to the run schema.** Overclaim persists.
